# Monomachine Nova 1.9.21 — Hotfix Track Delay, 30.09.2026

## Исправляемый симптом

В собранных **Synth** и **FX** при любом режиме DLY менялись значения `DSND` и
`DTIM` в интерфейсе, но слышимое эхо не реагировало; send оставался в подмесе.

## Причина

Это не изменение закона времени delay и не ping-pong-интерпретация DSND.
`DSND` остаётся ColdFire host-side Q23 mono-send.

У свежего состояния одновременно были открыты два маршрута:

- P1 EFFX `DSND=64`;
- P2 по умолчанию выбирал `FX-CHORUS`, имел `P2 MIX=127` и собственный
  `P2 DSND=64`.

Постоянный хвост второго TrackChain маскировал изменения P1: пользователь
слышал P2-return, а не результат редактирования `P1 DSND`/`P1 DTIM`.

## Исправление

1. У свежих экземпляров P1 и P2 `DSND=0`.
2. Новый P2 стартует как прозрачный `FX-THRU` с `P2 MIX=0`.
3. Для старых состояний добавлен одноразовый маркер
   `trackDelayDefaultRouteV1`. До его установки мигратор распознаёт только
   **полный точный** старый factory-набор P2 (CHORUS, его default words,
   `MIX=127`, `DSND=64`) и переводит этот P2 в `FX-THRU` / `DSND=0` /
   `MIX=0`.
4. Сохранённый P1 не меняется. Любое отклонение P2 от старого factory-набора
   отменяет миграцию: пользовательский P2 route и его значения сохраняются.

Таким образом, существующий намеренный P1 delay остаётся как был, но больше не
маскируется невидимым P2 factory-return. Для сознательного использования P2
нужно поднять `P2 MIX` и его собственный `P2 DSND`.

## Валидация исходников

Выполнено для обеих веток (`Monomachine_Nova_Synth` и
`Monomachine_Nova_FX`):

- `python3 verify_dsp_mode_patch.py` — PASS;
- `g++ -std=c++17 -fsyntax-only` для `PluginProcessor.cpp`,
  `P2RoutingTests.cpp` и `RollbackStateTests.cpp` с JUCE 8.0.12 — PASS;
- 17/17 portable строгих C++17 DSP-регрессий — PASS в каждой ветке, включая
  `DelayFeedbackDspTests`, Fix-5 vectors и FM-регрессии. Новые
  `P2RoutingTests.cpp` и `RollbackStateTests.cpp` отдельно прошли
  C++17 syntax-check вместе с реальным `PluginProcessor.cpp`.
- Прямой `DelayCore` probe на 44,1 кГц: при `DSND=0` wet не появляется;
  при send=1 первый tap для `DTIM=0/64/112/127` пришёл на
  `689/1378/5512/44101` samples соответственно. То есть DSND и DTIM
  реагируют в самом delay-core; исправление направлено на маршрут P1/P2.

Полная Windows VST3-сборка и прослушивание в DAW не выполнялись в этой Linux
среде; это обязательный финальный gate для выпуска бинарника.

## Короткая DAW-проверка

На новом экземпляре `DSND=0` не должен создавать хвост. Поднимите `P1 DSND`,
поиграйте ноту/подайте сигнал, затем меняйте `P1 DTIM`: слышимое время эха
должно меняться. Повторите для всех DLY modes и для Synth/FX. P2 проверяйте
отдельно, сначала намеренно подняв `P2 MIX` и `P2 DSND`.
