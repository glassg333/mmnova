# Monomachine SFX-60 OS 1.32B — данные, добытые из оригинальной прошивки (итерация 6)

**Дата:** 2026-09-20
**Прошивка:** `elektron_sfx6-60_os1.32b.bin` (8 388 608 байт)
**SHA-256:** `369849175602e20a9dd2b6e0ad8ac404b76f82718b14afbf1cbc01b7acabec7e`
**Железо:** Elektron Monomachine SFX-60 (ColdFire MCF5206e + 2× DSP56303, 44.1 кГц)
**Метод:** контейнер распакован `elektron-firmware-tool` (независимая MIT-реализация, лежит в репозитории `upload/eft`), далее собственный парсинг потоков HI08 и структур данных.

## 1. Что это

Пакет — результат шестой итерации добычи данных из оригинальной прошивки Monomachine.
В отличие от итераций 1–5 (см. `09_not_sorted/missing_data` в репозитории), где таблицы
восстанавливались из готовых образов `02_memory_images`, здесь **всё получено напрямую из
файла прошивки**: контейнер секций → распаковка → HI08-потоки загрузки DSP → образы памяти
DSP → заводские банки данных → строки/ресурсы ColdFire-части.

Главный результат итераций 5–6: **разобран полный конвейер загрузки DSP и подтверждена
бит-в-бит эквивалентность образов из прошивки эталонным образам репозитория.**
Это закрывает вопрос о происхождении `02_memory_images`: они полностью воспроизводятся
из OS-файла.

## 2. Верификация (главное доказательство)

Из HI08-потоков секций 1+3 (DSP1) и 2+3 (DSP2) пересобраны образы P/X/Y памяти обоих
DSP56303 и сравнены со словами с эталонными образами репозитория
(`02_memory_images/dsp{1,2}_{p,x,y}mem.bin`):

| Образ | Слов | Несовпадений |
|---|---|---|
| DSP1 P | 1 343 588 | **0** |
| DSP1 X | 1 044 | **0** |
| DSP1 Y | 1 076 | **0** |
| DSP2 P | 1 343 588 | **0** |
| DSP2 X | 1 044 | **0** |
| DSP2 Y | 1 279 | **0** |

То есть 100 % содержимого обоих DSP (код машин, wavetables, все таблицы) выводится из
файла прошивки без единого расхождения. Пересобранные образы лежат в
`03_dsp_images_from_firmware/`, отчёт — `03_dsp_images_from_firmware/verification.txt`.

Формат HI08-потока (запись func_7ce ColdFire): `[cmd LE24][addr LE24][count LE24][data LE24×count]`,
где cmd: 0 = P-банк, 1 = X-банк, 2 = Y-банк, 3 = JMP → конец потока (точка входа DSP, здесь всегда `0x66`).
Секции 1 и 2 — DSP-специфичные загрузки, секция 3 — общая для обоих DSP (133 записи, 111 912 слов P-банка).
Контрольные суммы хранилища секций сходятся (см. `06_reports/sections_checksums.txt`).

## 4. Новые результаты итерации 6

### 4.1 Структура секции 4 (заводские данные) — установлена

Секция 4 = 1 048 448 байт (`0xFFF80`). Константы подтверждены кодом OS
(`move.l #698,d4` @ секция0+`0x49e15`, `pea 4816` @ секция0+`0x49ea9`):

1. **Заголовок 0x28 байт.**
2. **Сетка слотов 698 байт (0x2BA) от 0x28**, минимум 130 слотов.
   Внутри слота имя (до 12 символов):
   - паттерны — имя в +0, нулевой паддинг;
   - киты — заголовок `ff 00` в +0..+1, имя в +2, паддинг символом `Z`.
   У китов **первые 2 символа имени перезаписаны байтами `ff 00`** — имена восстановлены
   по совпадению хвостов с полными именами (помечены `??`), часть восстановлена уверенно:
   `MULTI SAW/PULS/ENS/SID/DPRO/FM 1-3/FAT/SPLT/SIX4/BBOX`, `FREEJAZZ`, `TRUMMASKIN`,
   `RADIOWAVES`, `FUNKPATROL`, `COMPUTING`, `DIGITAL`, … Слот 1 = кит «THE FUTURE»
   (полн. имя восстановлено из «E FUTURE»).
   Классификация паттерн/кит эмпирическая (64 слота с именем в +0, 53 с `ff 00`+Z-паддингом);
   точное соответствие типам слотов OS — открытый вопрос.
3. **Зона песен:** сетка 4816 байт (0x12D0), база `0xE26E7`, 25 слотов до конца секции.
   Имена песен тоже частично «съедены» FF-заполнителем; уверенно читаются:
   `MM DEMO` (×2), `MONTORI`, `BLOCKSLUT`, `ASSSLUT`, `DELCRO`, `ASSTASS`, `WATERWALKR`,
   `BOOGIE`, `FREEWAVES`, `WARMART1`, `SUBSONIC`, `DELCIUS`, `POKEPEEK`; остальные —
   шаблон `NEW SONG`.
4. **Хвостовой блок** (последние ~0x240 байт, перед ним `MAGE`-фрагмент и указатель
   `fe8ab4`) — предположительно глобальные настройки.
5. Между сеткой 0x2BA и песнями — плотная зона ~837 КБ, структура не установлена
   (карта FF-прогонов в `zone_map.json`; там же лежит «зеркало» имен — второй набор
   блоков с теми же именами в обрезанном виде).

Все именованные слоты выгружены в `04_factory_data/slots/` и `songs/` — это готовые
заводские паттерны/киты/песни, которых в репозитории не было.

### 4.2 Строки и диагностика ColdFire-части

- Таблица версий OS в секции 0: строки `1.30 1.31 1.32 1.33 1.34 1.35 1.37 1.39`
  (офсеты `0x5331a+`, `0x534ff+`) — список версий, проверяемых при апгрейде/даунгрейде.
- Диагностика загрузки: `E: OS CHECKSUM`, `E: DSP CHECKSUM`, `E: DSP2 CHECKSUM`,
  `CHECKSUM`, `HOST TEST` — подтверждает контроль сумм секций при старте.
- Идентификация модели: `SFX-60+MK2`, `SFX-60MK2`, `MONOMACHINE SFX-60+ MKII`,
  `MONOMACHINE SFX-6+`, `MONOMACHINE SFX-60` (таблица имён устройств).
- Полный дамп — `05_main_os/strings.txt` (4640 строк), UI-тексты —
  `strings_os_uppercase.txt` (545 строк: меню, параметр-страницы, сообщения).

### 4.3 Карта P-банка

`03_dsp_images_from_firmware/p_bank_map.txt` — каждая из 133 записей секции 3
и DSP-специфичные записи секций 1/2 с адресами, размерами и привязкой к именам
таблиц из `04_tables/TABLES_MANIFEST.json` (SID, SWAVE, DPRO/BBOX, PHASER, FXDYN,
FX-REV, chorus-области и т. д.).

## 5. Открытые вопросы

1. Точная семантика слотов сетки 0x2BA (сколько паттернов, сколько китов, где граница)
   — нужен трассировщик записи/чтения флеш-банков в OS (кластеры обращений
   `0x185c6…0x1886c`, `0x439c4…0x44344` секции 0 уже помечены в итерации 5).
2. Почему у части китов/песен первые 1–2 символа имени затёрты `ff`-байтами —
   вероятно, артефакт заводского генератора данных.
3. Зона ~837 КБ между сеткой 0x2BA и песнями: не установлена (FF-прогоны
   0x400–0x1400 с регулярным шагом — возможно, второй банк слотов с крупными
   пустыми областями).
4. Назначение хвостового блока `0xFFD40…0xFFF80`.

## 6. Воспроизведение

Скрипты всех шагов — в `/scripts` исходного воркспейса:
`iter6_factory.py` (секция 4), `iter6_mainos.py` (секция 0), `iter6_pbank.py`
(образы DSP + карта), `iter6_pack.py` (сборка пакета); базовая распаковка —
`elektron-firmware-tool -i Elektron_SFX6-60_OS1.32B.syx -d 0..4 -o eft_sections`.
Верификация повторяется за минуту: пересобрать образы из `01_sections/` и сравнить
с `02_memory_images/` — ожидается 0 несовпадений.
