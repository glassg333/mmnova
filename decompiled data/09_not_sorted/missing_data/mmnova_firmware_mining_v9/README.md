# Monomachine SFX-60 OS 1.32B — данные, добытые из оригинальной прошивки (итерация 9)

**Дата:** 2026-09-20
**Прошивка:** `elektron_sfx6-60_os1.32b.bin` (8 388 608 Б)
**SHA-256:** `369849175602e20a9dd2b6e0ad8ac404b76f82718b14afbf1cbc01b7acabec7e`
**Метод:** дизассемблирование ColdFire-кода секции 0 (capstone M68K) + точное
сканирование абсолютных ссылок (фильтр по опкодам, только чётные смещения) +
статистическая проверка декода на всех 128 слотах. База — итерация 8 (v8).

---

## 1. Главный результат итерации 9

**Зона +0x557..+0x14D6 расшифрована полностью: это ПАРАМЕТР-ЛОКИ (parameter locks).**
62 строки × 64 Байта; строка = один (дорожка, параметр); байт = значение параметра
на данном шаге; `FF` = лока нет. Число активных строк — байт **+0x556**.
Все 323 строки 37 заводских слотов декодированы и привязаны к дорожкам
(0 непривязанных строк). Это закрывает открытые вопросы v8 №1 и №5.

### 1.1 Ключевые доказательства (ОС)

- **Счётчик строк +0x556:** при очистке паттерна ОС пишет туда 0
  (`move.b d1(0), (a0,d0.l)` при a0 = `$71703A`, OS 0x2D2EA — см.
  `disasm_pattern_clear.asm`); плеер получает число строк вызовом `jsr $224800`
  и крутит цикл `пока строка < число` (OS 0x351B6..0x351C4).
- **Ёмкость 62 строки:** при очистке ОС заполняет `FF` ровно 62 строки по 64 Б
  (цикл 0x2D2F2..0x2D304, `moveq #$3e` = 62) — от +0x557 до +0x14D6 включительно,
  что точно совпадает с границей хвоста +0x14D7 из v8.
- **Плеер строк (OS 0x34F9A..0x35188):** для каждой активной строки читает маску
  `банк + 0x274 + строка*8` (бит = шаг), а значение берёт из
  `банк + 0x557 + строка*64 + шаг`; сброшенный бит → `FF` в выходной буфер
  `$29B516` (d6 += 8 на группу битов маски).
- **Загрузчик слота (OS 0x34DB6):** копирует весь слот в рабочий буфер PAT3
  `$29817E` (`jsr $33A84`), затем копирует строки +0x557 по установленным битам
  масок (источник `банк+0x557+d7*64`, приёмник `PAT3+0x557+d6*64`, оба счётчика
  растут на установленном бите).
- **Очистка нот отдельным циклом:** 6 строк × 64 Б от +0x2A4 (база `$716D88`,
  OS 0x2D308..0x2D32C) — подтверждает размер нотной зоны 6×64.

### 1.2 Привязка строк к дорожкам (статистика, 64 заводских слота)

Позиции локов строки (байты ≠ FF) **всегда являются подмножеством тригг-позиций
ровно одной дорожки** (проверено на всех 323 строках: 0 исключений). Строки
одной дорожки идут в файле подряд (track-major). Распределение строк по
дорожкам: тр.0 — 148, тр.1 — 27, тр.2 — 41, тр.3 — 18, тр.4 — 54, тр.5 — 35.
Максимум строк в слоте — 42 (слот 1). Номер параметра внутри дорожки — открытый
вопрос v10 (нужен маппинг параметров машин по ID, ≤11 — из вектора +0x446).

Декод: `03_decoded/locks_decoded.json` — для каждого слота: длина, кит, число
строк, каждая строка = {дорожка, locked_steps: {шаг: значение}}.

### 1.3 Вопрос v8 №5 (+0x0C98) — ЗАКРЫТ

«Редкая зона +0x0C98 у слотов 1 и 16» — это просто строки локов 25..33
(0x0C98 = +0x557 + 29·64). Никакой отдельной структуры там нет.

### 1.4 RAM-архитектура паттернов (новая карта)

| Адрес | Что |
|---|---|
| `$294E8E` / `$296806` / `$29817E` / `$299AF6` | **4 буфера слота по 6520 Б** (шаг 0x1978); PAT3 — рабочая копия загружаемого слота |
| `$290E8E` | таблица шагов 64 × 256 Б, строится плеером (OS 0x34EA2..0x34F56, `jsr $3090C`) |
| `$29B46E` | массив записей stride **0xA8** (5+ записей, поля +0/+4/+0x40) после конца PAT4 |
| `$29B516` | выход распаковки локов плеера (d6 += 8 на группу) |
| `$716AE0` | номер текущего слота (банк = `$716AE4`) |
| `$7162A0` | **банк GLOBAL-слотов** (см. §1.5), `$71629C` — номер текущего |

### 1.5 GLOBAL-слоты — банк найден, карта построена (вопрос v8 №2)

Банк: секция 4, **+0x162A0, 8 слотов × 264 Б (0x108)** — ровно до базы банка
паттернов +0x16AE4. ОС копирует слот вызовом `pea $108; memcpy $22B532` в
`$29D0F0` (и вторую копию в `$29D1F8`); текущий номер — `$71629C`.

Карта полей из кода инициализации (OS 0x40B72..0x40CA8): +0=8, +2=6, +3=6,
+4=7, +9=2, +A/+B=1, +12=9, +13..17=`0A 0B 0C 0D 0E`, +18..1B=`01 02 07 0A`
(и ещё 5 копий), +30..35=`01`×6, **таблица 12 Б × 32 от +0x3C** (первый байт
каждой записи = 0x0B+12k — последовательные ID), +FD=0, +104..107=`00 00 11 30`.

Заводские данные: все 8 слотов имеют идентичный префикс 0x00..0x35 и тело
0x3C..0xFD; различаются только **+0x36..+0x3B** (6 Б, значения 0..0x7F) и
**+0xFE..+0x103** (6 Б; у слота 7 — восходящая последовательность
`08 09 0A 0B 0C 0D`). Дампы: `03_decoded/global_slots.json`.

### 1.6 Поле +0x554 (вопрос v8 №4) — аксессоры найдены

+0x554 — **знаковый байт** (используется `ext.w`), с тремя аксессорами:
getter `0x307E8`, **инвертированный getter `0xC0 − x`** (`0x30818`), очистка
`0x30852`. История: `+0x552 (слово) = sext(+0x554)`, затем `+0x554 ← +0x555`
(одиночная версия OS 0x2C384, цикл 128 слотов 0x3D5F2 из v8); при очистке
паттерна всё обнуляется. Значение пер-паттерновое, сохраняется в файле.
Семантика: транспозиция/свинг/BPM-оффсет — точный смысл остаётся открытым
(инверсия 0xC0−x намекает на смещение в полутон/цент-шкале).

### 1.7 Маски +0x274..+0x2A3 (вопрос v8 №3, частично)

Плеер читает эту зону с шагом **8 Б на строку локов** (`банк+0x274+строка*8`,
btst битов = шаги) — то есть это **маски активных шагов строк локов**, а не
«мелкие поля». Однако в заводских файлах байты зоны не коррелируют с позициями
локов (проверено на слотах 1/3/8/16) — вероятно, ОС поддерживает маски только
в рабочей копии RAM, а во флэш-файле зона содержит устаревшие данные. Маски A
(+0x1B0) / B (+0x1E0) — остаются на v10 (кандидаты accent/mute).

### 1.8 Хвост +0x14D7 (вопрос v8 №6) и киты (№7)

- Хвост = остатки журнала записи флэш: word-структуры с характерными сериями
  `0060 0160 0160 0460 0460 0460 0860 …` (шаг 0x40/0x60), индивидуальны у 59/64
  заводских слотов; формата журнала не восстанавливать из них — это мусор
  wear-leveling, а не данные паттерна.
- Киты: в файле ровно **один заводской кит (запись 1)** + 64 пользовательские
  записи (66..129) с телами-пустышками. Все 6 per-track записей по 72 Б кита 1
  **байт-в-байт идентичны**: `40 00 00 40 40 40 40 40 00 00 7F 00 …` — заводской
  шаблон параметров машин (0x40 = 64 = дефолт из v8). Привязка полей записи к
  параметрам машин остаётся открытой (нет вариативности для анализа).

## 3. Открытые вопросы для итерации 10

1. Номер параметра внутри дорожки для строк локов: нужен маппинг
   (ID машины из вектора +0x446 ≤11) → список параметров; дизассемблировать
   `jsr $2159CC` (установка значения по (шаг, параметр?)).
2. Семантика +0x554: сравнить значения с тональностями/транспозицией паттернов;
   проверить инвертированный getter 0xC0−x на заводских данных.
3. Маски A (+0x1B0) / B (+0x1E0): пер-дорожечные флаги; кластер кода
   0x2D8FC..0x2DFD6 (10+15 ссылок) — кандидат на дизассемблирование.
4. Назначение массива записей stride 0xA8 от $29B46E (поля +0/+4/+0x40).
5. Блок +0x4D0..+0x4F3 (6 Б × 6 дорожек, шаг 6 в коде 0x2D6C0..) — что это
   (векторы? микро-параметры?); уточнить v8-карту блоков 2 параметров.
6. Формат записей журнала хвоста +0x14D7 (если вообще имеет смысл — вероятен
   мусор wear-leveling).
7. Таблица 12 Б × 32 в GLOBAL (+0x3C, ID 0x0B+12k): что нумеруют ID.
