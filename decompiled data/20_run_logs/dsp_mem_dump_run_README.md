## 🏆 ГЛАВНОЕ ОТКРЫТИЕ

**Маркер `(v=3, b=255)` в сжатом потоке — это НЕ конец потока, а обычный матч с dist=256!**

Все предыдущие итерации использовали депакер с условием `off == 0xFF → EOF` (порт ColdFire-декомпрессора boot ROM `$1C4`). На самом деле поток **продолжается** через этот маркер (dist = 0x100 = 256). Из-за этого каждая «секция» прошивки была обрезана после первого встретившегося маркера:

| Поток | Было (EOF-версия) | Стало (noEOF) | Прирост |
|---|---|---|---|
| blk0 (ColdFire main) | 7 149 байт | **425 858 байт** | **59.6×** |
| blk1 (DSP1 internal) | 10 744 байт | **11 226 байт** | +4.5% |
| blk2 (DSP2 internal) | 10 528 байт | **11 022 байт** | +4.7% |
| blk3 (DSP common) | 19 898 байт (133 зап.) | **336 945 байт (135 зап.)** | **16.9×** |
| blk4 (фабрика, не знал никто) | — | **1 048 448 байт** | NEW |
| **ИТОГО** | **48 319 байт** | **1 833 499 байт** | **×37.9** |

**Доказательство корректности:** депак блока 0 с семантикой noEOF даёт **ровно** `coldfire_main.bin` из `05_descriptors/` (425 858 байт, бит-в-бит, SHA-256 совпадает). Все 4 прежних «хвоста секций» (в т.ч. загадочные 291 КБ после старых 133 записей) — это продолжения тех же потоков. Ничего не осталось неразобранным: каждый поток разобран на 100% (`consumed == len`).

## Как был найден формат (boot ROM, дизассембл)

Boot ROM ($0..$4000) строит цепочку указателей из первых long каждого блока (совпадают с полями `[slen BE32]`):

```
a0 = $4000 + [ $4000 ] + 8          = $2C6EC   (blk1)
a0 += [ $2C6EC ]                    = $2E5AA
a0 += [ $2E5AA + 8 ]                = $30411   (blk3)
a0 += [ $30411 + $10 ]              = $79B8A
src = a0 + $20 = $79BAA → биты с $79BB2        (blk4!)
depack(src+8, dst=$100000)                     (jsr $1c4 @ $224A)
depack(src=$4000, dst=$200000); jmp $200000    (jsr $1c4 @ $2316 — запуск main)
```

Формат записи HI08 подтверждён: `[cmd LE24][addr LE24][count LE24][data LE24×count]`, cmd: 0=P, 1=X, 2=Y, 3=JMP P:addr (поток продолжается!), 4=END. Потоки blk1/blk2 начинаются с `JMP P:$0066` — точка входа DSP-ядра.

## Верификация: образы DSP объяснены полностью

Реконструкция P-памяти из записей blk1/blk2/blk3:

- **0 расхождений** с `dsp1_pmem.bin` и `dsp2_pmem.bin` (все 111 912 + 2 861 + 2 788 слов)
- Непокрытая область образов (1 228 815 слов) — **нулевая в обоих образах**: никаких «неизвестных данных» в образах не осталось
- Coverage: `P:$100000..$1134C3` (79 044 сл.) + `P:$140000..$148063` (32 868 сл.) из blk3; внутренние `P:$0..$BA2` из blk1/blk2

**Diff ядра DSP1 vs DSP2: 686 слов** (файл `dsp1_vs_dsp2_kernel_diff.txt`) — все различия во внутренней области `P:$000000..$000B4C`. DSP1 (mixer/main) и DSP2 (producer) исполняют **разный kernel-код**: несовпадают векторы/таблицы ветвления ($0D..$21), обработчики ($66..$C7), блоки кода ($152..$31F). Внешняя память (машины + таблицы) идентична.

## НОВЫЕ данные, которых не было в итерациях 1–3

### 1. Банк 64 заводских вейвформ (`factory_wavetables/`)

`BIN $100000..$15FEFE`, структура входа: `[1a][idx][cksum][name4][данные ~6132 Б]`, индексы 0..63 без пропусков:

| Слоты | Имена |
|---|---|
| 0–7 | SINE, HSIN, WTRI, ZOID, RSQR, DSAW, ISAW, QRND |
| 8–15 | SYN1…SYN8 |
| 16–28 | ORG1…ORG9, ORGA…ORGD |
| 29–31 | ELP1…ELP3 |
| 32–39 | STR1…STR8 |
| 40–47 | WND1…WND8 |
| 48–55 | MALA, MALO, MALU, MAL[, MALE, MALI, MAL\, MAL] |
| 56–63 | FEMA, FEMO, FEMU, FEM[, FEME, FEMI, FEM\, FEM] |

Это заводские вейвтаблицы машины SWAVE/SUPERWAVE (загружаются в DPRO/SWAVE слоты). **Кодирование сэмплов — открытый вопрос итерации 5** (данные не являются плоскими BE24-словами; вероятно, свой упакованный формат — понадобится реверс SWAVE-загрузчика в coldfire_main.bin, который теперь доступен целиком).

### 2. Банк заводских пресетов (blk4, 1 048 448 Б)

`blk4_full.bin` — декомпрессированный блоб с паттернами/китами фабрики (строки «SUPERWAVES», «PULSES», «SIXSIDS», «WAVEMIX», «TRENCHED», «IGOTGAME»…, повторяющиеся структуры ~1805 слов). Ранее эта область вообще не фигурировала в реверсе.

### 3. Полная карта записей загрузчика (`loader_records/`)

162 записи (13 + 14 + 135) с адресами, длинами и SHA-256 каждого блока данных. Границы записей blk3 = **семантическая нарезка** внешнего кода/данных (каждая запись — логический юнит загрузчика). Ключевые диапазоны: `P:$100000..$1134C3` — kernel+машины, `P:$140000..$148063` — машины+таблицы (совпадает с картой аудита).

### 4. Math-таблицы (контрольная генерация)

`X_14A000_sine_table_8K_math.bin`, `X_14A800_width_table_chorus_B_math.bin` — sin/cos 8192 точек × 24-bit BE по формулам из KERNEL_VOICE_CHAIN.md (закрывают последние 2 «math-recoverable» позиции аудита).
