Резонансы HPQ / LPQ и модулятор фильтра

Новый источник: Jick238/monomachine-lab — рабочий эмулятор на настоящей прошивке

1. Твой роутинг подтверждён независимо A

Ты проверил на слух: synth → dist → eq → srr → filt → env → dsnd

CHANGELOG эмулятора monomachine-lab (он гоняет настоящую прошивку в dsp56kEmu) пишет дословно:

«Kept the original machine, distortion/SRR, filter, EQ, AMP and delay routines»
Совпадает
  • • DIST идёт рано, сразу после машины
  • • AMP/ENV идёт после фильтра
  • • delay / DSND — последний
  • • SRR — до фильтра, не после
Расходится в мелочи

У тебя eq → srr → filt, в CHANGELOG srr → filt → eq. Твой слуховой тест сильнее — там прямое сравнение. В CHANGELOG это перечисление подпрограмм, не обязательно порядок.

Важно: это снимает противоречие с KERNEL_VOICE_CHAIN.md, где было «AMP env → LFO → SVF». Там описан порядок блоков кода внутри func_0004A8: сначала считается значение огибающей, потом LFO, потом фильтр. А умножение звука на огибающую происходит в конце. Обе картины верны.

2. Канонические имена всех параметров A

Из core/monomachine_engine.h — enum эмулятора, который реально гоняет прошивку. Это снимает все вопросы по именам и порядку.

enum class Parameter : uint8_t {
  AmpAttack, AmpHold, AmpDecay, AmpRelease,
  AmpDistortion, AmpVolume, AmpPan, AmpPortamento,

  FilterBase, FilterWidth, FilterHighPassQ, FilterLowPassQ,
  FilterAttack, FilterDecay, FilterBaseOffset, FilterWidthOffset,

  EffectEqFrequency, EffectEqGain, EffectSampleRateReduction,
  EffectDelayTime, EffectDelaySend, EffectDelayFeedback,
  EffectDelayBase, EffectDelayWidth,

  SynthA .. SynthH,  TrackLevel
};

Значения хранятся в исходном разрешении 0..127 («Values retain the original 0..127 resolution»). Два резонанса — FilterHighPassQ и FilterLowPassQ. Модулятор — FilterAttack / FilterDecay / FilterBaseOffset / FilterWidthOffset.

3. Найдена база страницы параметров A

static constexpr uint32_t kVoicePageYAddress = 0x000500;

Складываем с известным из ядра: голос V = Y:$528, а страничные параметры лежат в V-$28 .. V-$01.

$528 − $28 = $500 — сходится точно.

То есть все 40 слов страничных параметров занимают Y:$500..Y:$527. Это та самая область, куда ColdFire пишет уже пересчитанные в fixed-point значения ручек. Теперь у неё есть подтверждённый адрес.

4. Побочные находки

  • • Домен питча подтверждён: «the scheduler's actual note domain uses 0x800 per octave with a 0x5800 pre-offset». Это ровно 2048 шагов на октаву и 11 октав — сходится с X:$140000. Калибровка: GND-SIN даёт 261.6 Гц на MIDI 60.
  • • Баг экстрактора подтверждён в оригинале. В 07_scripts/repo/extract_tables.py буквально стоит if base_addr >= 0x100000: off = base_addr - 0x100000. Мой фикс верен.
  • • Новые адреса таблиц из докстринга того же скрипта: FX-DYN RMS P:$144746 (~64), reverb delay buffer X:$120000 (~8192), DPRO wavetable X:$11B451.
  • • «EQ band table X:$140000» в том скрипте — ошибочное имя. Аудит доказал, что это таблица питча wt[i]=0.5·2^(i/2048) с точностью 1e-9. А $1407FF = её конец, читается с отрицательным индексом (видно в FX-DYN и SWAVE-ENS).

Гипотеза: «LFO INTL/DPTH» в доке — это на самом деле модулятор фильтра B

Автор доки сам пометил это как открытый вопрос (§9 п.2: «точное назначение INTL/DPTH веток (P:$53E-56C) — требует трассировки»). Вот почему я думаю, что там фильтр:

Довод 1 — расположение
Блок $50C..$50F стоит вплотную перед $508(BASE-множитель) и внутри того же куска P:$537–$5D2, который считает срез. Если разложить FILT-страницу подряд начиная с $508, получается ровно: BASE, WDTH, HPQ, LPQ, ATK, DEC, BOFS, WOFS → $508..$50F. И $508 действительно используется как база среза — это уже подтверждено.
Довод 2 — формула выдаёт биполярность
Док §4.5: |Y:(V-$1A) + $C00000| × $700. В 24 битах $C00000 = −$400000, то есть это |x − 0.5| — классическое взятие модуля от биполярного параметра, где центр = $400000. BOFS и WOFS как раз биполярные (−64…+63). У однополярного SPD такой центровки быть не должно.
Довод 3 — LFO живёт в другом месте
LFO1/2/3 — это отдельные страницы, и в enum эмулятора их вообще нет среди 33 автоматизируемых параметров (только AMP / FILT / EFFX / Synth / Level). Состояние LFO док помещает в отдельное окно r7 = V+$B4, а не в страничный блок.
Довод 4 — общая таблица скоростей
Док сам отмечает, что Y:$141800 — общая таблица для «LFO SPD и AMP env rates». Огибающая фильтра логично берёт скорость оттуда же. Блок, который автор назвал «LFO-фаза», по структуре неотличим от генератора огибающей.

Если гипотеза верна, картина такая:

Y:$508 = BASE     Y:$50C = FILT ATK  → rate Y:$141800
Y:$509 = WDTH     Y:$50D = FILT DEC  → rate Y:$141A00
Y:$50A = HPQ      Y:$50E = BOFS      → |x−$400000|·$700  (биполярный)
Y:$50B = LPQ      Y:$50F = WOFS      → вторая такая же ветка

env = envelope(ATK, DEC)
BASE' = BASE + env·BOFS      WDTH' = WDTH + env·WOFS

                    ↓

Это гипотеза, не факт. Проверяется одной командой — см. следующую вкладку.

Способ, который сильнее дизассемблера: измерить на живой прошивке

monomachine-lab — не порт, а эмулятор dsp56kEmu, который исполняет настоящий бинарь прошивки. Значит его выход = выход железа. И у него есть ровно то, что нужно:

bool setParameter(Parameter parameter, uint8_t value);   // 0..127
bool renderBlock(Block& destination);                    // 16 кадров стерео
uint32_t debugXWord(uint32_t address);                   // ← читать X-память!
uint32_t debugYWord(uint32_t address);                   // ← читать Y-память!

Последние два метода решают задачу напрямую. Не нужно разбирать опкоды — можно подсмотреть, что прошивка сама положила в память.

План A — проверить гипотезу за 5 минут

Ставим HPQ в 0, читаем весь блок Y:$500..$527. Потом ставим HPQ в 127 и читаем снова. Какое слово изменилось — там и живёт HPQ. Повторить для LPQ, BOFS, WOFS, DIST.

// псевдокод на базе их же API
for (int addr = 0x500; addr <= 0x527; ++addr) before[addr] = eng.debugYWord(addr);

eng.setParameter(Parameter::FilterHighPassQ, 127);
eng.renderBlock(blk);                     // дать прошивке применить

for (int addr = 0x500; addr <= 0x527; ++addr) {
    uint32_t now = eng.debugYWord(addr);
    if (now != before[addr])
        printf("HPQ живёт в Y:$%03x : %06x -> %06x\n", addr, before[addr], now);
}

Это даёт точный адрес каждой ручки в странице — то, что в доке репо числится открытым вопросом №1.

План B — снять кривую Q целиком

Как только адрес известен, гоняем ручку 0…127 и пишем, что прошивка кладёт в память. На выходе — готовая таблица на 128 значений, вообще без реверса.

for (int v = 0; v <= 127; ++v) {
    eng.setParameter(Parameter::FilterHighPassQ, v);
    eng.renderBlock(blk);
    printf("%3d  Y:$50a=%06x   q=%+.9f\n",
           v, eng.debugYWord(0x50a), toFloat(eng.debugYWord(0x50a)));
}

То же самое для Y:$91+ — там лежат уже готовые f и q, которые читает петля SVF. Снимешь их — и заглушка cutoffCoeff() в моём коде заменяется реальной таблицей.

И так же снимается кривая DIST, которую иначе пришлось бы выковыривать из ColdFire через capstone M68K.

План C — если эмулятор собирать не хочется

В core/monomachine_engine.cpp (44 КБ) есть функция с готовым ответом:

static std::size_t parameterPageOffset(Parameter parameter) noexcept;

Она отображает каждый параметр в смещение внутри страницы. Достаточно её найти:

grep -n -A60 "parameterPageOffset" core/monomachine_engine.cpp

Файл 44 КБ — мой загрузчик его обрежет, а у тебя прочитается целиком. Кидай вывод, разберу.

Почему я не могу сделать это сам

Ядро dsp1_kernel_P0000-0B4D.txt = 102 КБ, мой загрузчик отдаёт первые ~10 КБ и рвёт на $00EB. Проверил четыре пути: raw.githubusercontent (text и markdown), jsDelivr CDN, GitHub API в base64, прокси r.jina.ai — все обрываются в одном месте, значит лимит мой, не серверный. Регион $0537–$05FA лежит примерно на 48 КБ вглубь. Бинарные .bin я не читаю вообще.
