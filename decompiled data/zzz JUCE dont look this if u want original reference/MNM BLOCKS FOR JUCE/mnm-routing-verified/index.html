EQ — до фильтра (у тебя) или после (в CHANGELOG). Всё остальное сошлось. Твой слух здесь весомее: в CHANGELOG это перечисление подпрограмм, необязательно порядок вызова.

Про AMP/env: ты и CHANGELOG ставите его после фильтра, PAGE_TEMPLATES — до. Противоречия нет: в func_0004A8 сначала вычисляется значение огибающей (потому оно и «первое» в описании блоков), а умножение звука на него происходит в конце. Обе картины верны, просто описывают разное.

Роутинг буферов — теперь с адресами инструкций A

Из 3 mnmdsp_reference/dsp/MnmRouting.h и docs/ROUTING_RU.md. Это закрывает вопрос «как звук попадает в FX-машину».

Буферы   X:$2C0..$2C3 = { $160, $1C0, $220, $280 }     (DSP1)
         buf0/1/2 = выходы 3 треков текущего прохода
         buf3     = внешний вход (codec ADC)

Выбор входа машины   P:$0113-$0131, флаги X:$2C4 (пишет ColdFire)
   bit4  → r0 = буфер 3 (EXT)
   bit12 → r0 = буфер 0
   bit13 → r0 = буфер 1
   иначе → r0 = буфер 2

Заливка EXT          P:$02ED-$031D   (bit6/7, пинг-понг X:$100/$120)
Запись выхода        P:$0143-$0218
   бит установлен → ПЕРЕЗАПИСЬ  func_0001ec   ← INSERT
   бит сброшен    → ДОБАВЛЕНИЕ  func_0001e2   ← параллельно
Сумма в микс         func_0001A3, P:$01AD-$01C1 : buf0+buf1+buf2 → buf0

Почему «6 треков, а сосед только один»: голоса идут по 3 за проход, и выбрать можно только буфер своего прохода. Железо физически не даёт больше трёх источников плюс внешний вход.

«100% wet» — это роутинг, а не MIX: FX читает буфер соседа и перезаписывает тот же буфер → стоит инлайном в его пути, сухой заменяется. В коде машин никакого «особого режима соседа» нет — машина не знает, откуда пришёл вход.

INP и MIX — точные формулы A

INP   P:$14768B-$147698   gain = INP² , ×4 на произведении в 56-бит ДО сатурации
      ручка 32  → −12 дБ
      ручка 64  →   0 дБ   (слово 0.25, эф. гейн 1.0)
      ручка 127 → +12 дБ   (слово 1.0,  эф. гейн 4.0)     закон квадратичный

MIX   P:$1477CB-$1477DD   x0 = MIX (слово V+$07)
      a = $7FFFFF − x0                     ; вес сухого
      out = a·dry + x0·wet                 ; на каждый из 16 кадров
      одинаково у CHORUS / REVERB / DYNAMIX / PHASER / FLANGER / RINGMOD
      MIX везде = p3

Дефолты прошивки: MIX = 127 у CHORUS, DYNAMIX, PHASER, FLANGER; у REVERB = 32. Из коробки эти машины почти полностью wet.

Главное: кривые ручек — это ДАННЫЕ, а не код

Я раньше говорил, что кривую Q придётся выковыривать дизассемблером ColdFire через capstone M68K. Это было неверно. ROUTING_RU.md §6 пишет прямо:

«Точный скейлинг каждой ручки (кривые в raw_tail дескрипторов, формат не расшифрован)»

То есть они лежат таблицей внутри блока дескриптора, который уже извлечён. Дизассемблер не нужен — нужно просто правильно разобрать 176 байт.

Формат блока дескриптора (шаг 0xB0 = 176 байт)

+0x00   short name      ("GND" / "FX" / "SWAVE" ...)
+0x09   display name    ("SIN" / "CHORUS" ...)
+0x12   параметры       8 × 6 байт = 48 байт   ← 4 байта имя + 2 байта ???
+0x42   defaults        8 байт
+0x4A   ...             102 байта — RAW_TAIL, не расшифрован
+0xB0   конец блока

Два кандидата, где сидят кривые: хвостовые 2 байта каждого параметра (8 × 2 = 16) и/или raw_tail на 102 байта.

Косвенное подтверждение, что типы кривых существуют

В 1 try/Source/mmnova/machines/MnMSid.h автор писал:

«Кривые дескриптора: PWRS/WAVE/MOD/MSRC — ступенчатые (тип 02/05/04/02)»

Значит он уже видел байт типа кривой у каждого параметра. Коды: 02 = ступенчатая, плюс 04 и 05.

⚠ Осторожно: fx_descriptors.json разобран НЕВЕРНО

Проверил 05_descriptors/fx_descriptors.json — парсер съехал по смещениям. Пользоваться им нельзя:

ПолеВ jsonДолжно быть
display m12"HRU""THRU" (T ушла в name_tag=84)
params m15DEL, P, "", FB, D, "", "@@@\x7f"DEL DEP SPD MIX FB WID LP INP
defaults[128,0,0,0,128,0,0,0] у всеху CHORUS 40 40 40 7F 00 00 7F 40

Видно, что парсер читает с шагом 4 вместо 6 и не учитывает, что имя занимает 4 байта. При этом all_machine_descriptors.json (и собранный из него MnmParams.h) — корректен: там дефолты сходятся с мануалом.

Полезный побочный эффект: в кривых m14 мелькают ненулевые байты 0x80 0x00 0x25 0xf2 и 0x60 0x00 0x25 0xf2. Даже при кривом парсе видно, что там реально лежат данные, а не нули.

Но есть нюанс: HPQ/LPQ — не в машинном дескрипторе

Машинные дескрипторы описывают только SYNT-страницу (8 ручек конкретной машины). А HPQ/LPQ/BOFS/WOFS живут на общей FILT-странице, одинаковой для всех машин.

Значит должен существовать отдельный блок дескрипторов страниц — AMP / FILT / EFFX / LFO. Косвенное доказательство: файл PAGE_TEMPLATES.txt помечен «verified from ColdFire main», то есть автор его откуда-то прочитал. Скорее всего рядом с 0x57FC5, до или после блока машин.

Сверка номеров слотов — есть расхождение

В MnmParams.h из папки 3 DDRW и DENS стоят как слоты 20 и 21. В аудите репо и в дизассемблере они проходят как m22 и m23, а слайсы лежат в файлах с именами 32_FX-DLY и 33_FX-EXT.

Это не критично для звука (порядок ручек одинаковый), но при сборке диспетчера надо решить, какая нумерация используется. Я бы держался номеров из таблицы диспетчеризации X:$10016B, а не из порядкового индекса в дескрипторах.

Три способа получить кривые HPQ / LPQ / DIST. От лёгкого к тяжёлому

ПУТЬ 1 — проще всего парсинг данных, без реверса

Перечитать блоки дескрипторов правильно. Формат известен: шаг 176 байт, параметры 8×6 с +0x12, дефолты с +0x42, дальше 102 байта хвоста.

python - <<'EOF'
d = open("decompiled data/05_descriptors/coldfire_main.bin","rb").read()
base, stride = 0x57FC5, 0xB0
for i in range(26):
    b = d[base+i*stride : base+(i+1)*stride]
    if len(b) < stride: break
    print(f"--- блок {i}  @0x{base+i*stride:05x}")
    print("  short   :", b[0:9])
    print("  display :", b[9:0x12])
    for p in range(8):
        q = b[0x12+p*6 : 0x12+(p+1)*6]
        print(f"  p{p}: имя={q[0:4]}  хвост={q[4]:02x} {q[5]:02x}")
    print("  defaults:", " ".join(f"{x:02x}" for x in b[0x42:0x4A]))
    print("  raw_tail:", " ".join(f"{x:02x}" for x in b[0x4A:0xB0]))
EOF

Смотрим на два хвостовых байта каждого параметра. Если у ступенчатых (WAVE, MOD, MSRC) там 02/04/05, а у плавных что-то другое — формат разгадан. Дальше ищем такой же блок для страниц AMP/FILT.

ПУТЬ 2 — точнее всего измерение на живой прошивке

У monomachine-lab в API есть debugYWord(). Крутим ручку и смотрим, что прошивка сама кладёт в память. Результат — не гипотеза, а факт.

// шаг 1: найти адрес ручки в странице Y:$500..$527
uint32_t before[0x28];
for (int a=0; a<0x28; ++a) before[a] = eng.debugYWord(0x500+a);
eng.setParameter(Parameter::FilterHighPassQ, 127);
eng.renderBlock(blk);
for (int a=0; a<0x28; ++a)
    if (eng.debugYWord(0x500+a) != before[a])
        printf("HPQ -> Y:$%03x\n", 0x500+a);

// шаг 2: снять всю кривую
for (int v=0; v<=127; ++v) {
    eng.setParameter(Parameter::FilterHighPassQ, v);
    eng.renderBlock(blk);
    printf("%3d %06x\n", v, eng.debugYWord(НАЙДЕННЫЙ_АДРЕС));
}

Так же снимаются LPQ, BOFS, WOFS, DIST и готовые f/q из Y:$91+.
