# Восстановление CHORUS: источник и границы переноса

## 1. Откуда взят алгоритм

Исходный репозиторий: https://github.com/glassg333/mmmm

Проверенная ревизия `main`: `e84501f512dd3d7d03a60dbf8a640ce70fb4f6f6`.

Прошивка: `elektron_sfx6-60_os1.32b.bin`, 8 388 608 байт.

SHA-256:

```text
369849175602e20a9dd2b6e0ad8ac404b76f82718b14afbf1cbc01b7acabec7e
```

Готовый файл `dsp/monomachine_chorus.hpp` из этого репозитория **не является источником реализации**: в нём другая, значительно более простая схема и отсутствуют FB/LP/INP. Заголовки и описания README сами по себе не принимались за доказательство точности.

Полного листинга CHORUS в проверенной ветке не было. Поэтому DSP был извлечён и дизассемблирован из находящегося там BIN.

## 2. Проверенная цепочка извлечения

1. По смещению ROM `0x4000` найден контейнер обновления длиной 516 024 байта.
2. Проверено **полное побайтовое совпадение** этого диапазона с контейнером, восстановленным из SYX того же репозитория, а не только несколько сигнатур.
3. Далее секции повторно распакованы **непосредственно из BIN**. Проверены длины и контрольные суммы сжатых секций.
4. DSP-поток разобран как little-endian 24-битные слова. Начальный и конечный маркеры: `[3, 0x66]`. Записи между ними: `[area, address, count, payload…]`, где 0=P, 1=X, 2=Y. Проверены границы каждой записи.
5. Отделены заголовки загрузки, таблицы и исполняемый код. Таблица диспетчеризации сверена с реально загруженной памятью.
6. Изолированный машинный код CHORUS из BIN побайтово совпал с кодом по соответствующим адресам загруженного DSP.

Для распаковки применялся MIT-инструмент `mischa85/elektron-firmware-tool`; для дизассемблирования и отладочной загрузки — инструменты DSP56300/Gearmulator. Они использовались **только при анализе**.

## 3. Реальные адреса

Индекс машины CHORUS — **15**.

| Назначение | Ячейка таблицы P | Значение / вход процедуры P |
|---|---|---|
| Init | `$10017A` | `$147661` |
| Config | `$10019C` | `$14767A` — `RTS` |
| Process | `$1001BE` | `$14767B` |

Последняя инструкция процесса — `RTS` по `$1477DD`. Следующий блок начинается по `$1477DE` и в ядро не перенесён.

Весь блок — **381 слово / 1 143 байта / 292 инструкции**. Конфигурация использует заключительный `RTS` init; это не отдельный скрытый алгоритм.

`Analysis/chorus-raw.asm` содержит листинг. `Source/dsp/ChorusCore.cpp` содержит статические C++-операции с исходными адресами в комментариях. Не выполняется декодирование опкодов, нет программного счётчика, JIT, виртуального DSP или загрузки ОС.

## 4. Что делает процедура

| Адреса P | Стадия |
|---|---|
| `$147661–$14767A` | Начальная память, фазовое состояние, указатель задержки |
| `$14767B–$147688` | Начальное приглушение wet на 128 блоков |
| `$147689–$147698` | Входной коэффициент INP и перенос 16 стереокадров |
| `$147699–$1476AB` | Рекурсивный генератор модуляции со fixed-point насыщением |
| `$1476AD–$147701` | Сглаживание WID, поворот фаз, дополнительные фазовые ветви |
| `$147702–$14774A` | DEL/DEP, 48-битные состояния, формирование дробных задержек |
| `$14774D–$14776C` | Чтение шести отводов с исходной дробной интерполяцией |
| `$14776E–$147785` | Суммирование трёх отводов на канал |
| `$147787–$14779D` | LP-фильтрация возврата обратной связи |
| `$14779E–$1477CA` | FB, входная примесь и запись кольцевых буферов |
| `$1477CB–$1477DD` | MIX и выход 16 стереокадров |

Сохранены порядок параллельных переносов DSP, фиксированные размеры циклов, лимитирование переносов и арифметическое насыщение. Перестановка чтения/умножения/записи здесь может менять младшие биты и фазовые состояния; поэтому схема не заменялась «похожим» float-chorus.

### ABI выбранного одиночного экземпляра

- Вход: X-память, `R0=$220`.
- Выход: Y-память, `R7=$100`.
- База состояния: `R6=$528`.
- DEL…INP поступают в `Y:(R6+$4)` … `Y:(R6+$B)`.
- Рабочие временные данные: локальные X/Y-области.
- Два кольцевых буфера по 2 048 сэмплов: внешняя память от `$114000`, второй канал со смещением `$800`.

Во внешней области X/Y/P у исходной аппаратуры общая память. Запись через X и чтение через Y в коде CHORUS относятся к **одному буферу**, а не к двум несвязанным массивам.

Имена `a`, `b`, `r[]` и адресные комментарии оставлены для проверяемой связи с листингом. Они являются обычными переменными компилируемых функций, а не состоянием исполняемой виртуальной машины.

### Таблицы

- LP: запись исходной DSP-секции по `$144AC7`, 258 слов; параметры используют её начальную часть.
- WID: две смежные таблицы по `$14A000` и `$14A800`, всего 4 096 слов. Они формируются при загрузке ОС и сняты из её реально загруженной памяти.

WID не пересчитан через `std::sin`: такой пересчёт давал отличающиеся младшие биты. В плагине сохранены исходные целые коэффициенты. При независимой проверке эталон читает их из исходного снимка памяти, а **не из C++-заголовка плагина**.

## 5. Важная поправка к отладочному эталону

У использованной ревизии интерпретатора DSP56300 обнаружено: функция насыщения присутствует, но в пути обычного MPY/MAC не вызывается. CHORUS явно включает `SR.SM` инструкцией `BSET #$14,SR` перед рекурсивной модуляцией. Игнорирование этого бита даёт различия после выхода накопителя за диапазон.

Режим и границы арифметического насыщения описаны в **DSP56300 Family Manual, раздел 3.2.3**: результат ограничивается 48-битной дробной частью. [1](https://www.nxp.com/docs/en/reference-manual/DSP56300FM.pdf)

В **исследовательском интерпретаторе**, отдельно от плагина, добавлен вызов его существующей функции насыщения после MPY/MAC. Патч: `Analysis/oracle-SM-correction.patch`. Исходный алгоритм CHORUS и код плагина ради совпадения с неполным эмулятором не упрощались.

Поэтому результат проверки корректно формулируется так: **построчный перенос совпадает с исполнением исходной процедуры в интерпретаторе с указанной поправкой SM**. Это не заявление о проведённом аппаратном побитовом A/B.

## 5.1 Единственное сознательное отклонение: MIX=127 — полный wet

В исходной процедуре MIX=127 даёт `x0 = 127·65536 = $7F0000`, а вес сухого сигнала вычисляется как `0x7FFFFF − x0 = $7FFF`. Поэтому даже при полном вклёпе эффекта выход содержит ~0,78% сухого сигнала и ~0,78% недокомпенсации wet (остаток исходной арифметики, а не ошибка переноса).

По решению заказчика добавлено **единственное** сознательное отклонение от исходных инструкций: сразу после `P:$1477CF` при `x0 = $7F0000` он принудительно устанавливается в `$7FFFFF`. Тогда:

- MIX=127 → выход = 100% wet (fixed-point-точно: коэффициент `$7FFFFF/2^23`, отклонение ≤ 1 LSB, −138 дБ), сухой сигнал отсутствует;
- MIX=0 → выход = dry (±1 LSB, как в исходной процедуре);
- все остальные значения MIX и все остальные стадии побитово совпадают с исходными инструкциями.

Из-за отклонения контрольный хеш нативного теста изменился: `7007ca4d75708b0f` (побитовый с ROM) → `5fa13bb709f68782` (с клэмпом). Независимое сравнение с эталонами исходных инструкций (103 809 024 слова, 0 расхождений) выполнялось **до** введения отклонения и зафиксировано в `TestsResults/original-instruction-comparison.txt`; запись о нём — в `Analysis/provenance.json` (`deviations`).

## 6. Что остаётся за границей машины

В JUCE реализованы только оболочка эффекта, параметры, состояние, GUI и транспорт частоты дискретизации. Эти части необходимы для плагина и не выдаются за код Elektron.

Не перенесены общая маршрутизация, AMP/FILTER/EFFECTS, sequencer, универсальные LFO назначений, АЦП/ЦАП и служебная CPU-доставка параметров. Восьмёрка значений 0–127 подаётся в аргументы процедуры; внутреннее сглаживание CHORUS сохранено. Отсутствие внешнего CPU-сглаживания означает, что жесты автоматизации не следует объявлять тождественными повороту энкодера физического прибора.

Частота ядра 44,1 кГц фиксирована. Внешний sinc SRC применяется только для согласования с другой частотой проекта DAW. При 44,1 кГц SRC полностью обойдён.
